# Лабораторная 2 по дисциплине "Технологии программирования"

**Тема:** изучение фреймворка MVC.

## Цели работы

1. Познакомиться с моделью MVC, её сущностью и основными фреймворками на её основе.
2. Разобраться с сущностями «модель», «контроллер», «представление» и их функциональным назначением.
3. Получить навыки разработки веб-приложений с использованием MVC-фреймворков и написания модульных тестов к ним.

## Постановка задачи

За основу взят учебный интернет-магазин на Django ([kpdvstu/PTLab2](https://github.com/kpdvstu/PTLab2)).

**Индивидуальное задание, вариант 10:**

| Тип магазина | Функциональность приложения |
|---|---|
| Магазин одежды | При одновременной покупке экземпляров товаров разного вида на общую сумму покупки предоставляется скидка 10%. |

Дополнительно: выбрать лицензию; доработать магазин в отдельной ветке и влить её в основную;
составить модульные тесты; сделать выводы.

> Автоматическое развёртывание (Travis CI + Heroku) в этой работе не выполнялось: из проекта убраны
> `.travis.yml`, `Procfile` и зависимости `django-heroku`, `dj-database-url`, `gunicorn`, `whitenoise`.

## Описание решения

### Бизнес-правило

Заказ может содержать несколько позиций (товар × количество). Если в заказе **не менее двух разных
товаров** с ненулевым количеством, на **всю сумму** заказа даётся скидка 10% (с округлением до копеек).
Если куплено несколько экземпляров одного товара, скидки нет.

| Заказ | Сумма | Скидка | Итого |
|---|---|---|---|
| Футболка × 2 + Джинсы × 1 | 5900 | 590.00 | 5310.00 |
| Куртка × 2 | 17800 | 0 | 17800 |

### Распределение по слоям MVC (в терминах Django — MTV)

| Слой | Файлы | Ответственность |
|---|---|---|
| **Model** | `shop/models.py` | `Product`, `Purchase` (заказ: покупатель, адрес, сумма, скидка, итог), `PurchaseItem` (позиция: товар, количество, цена на момент покупки) |
| Бизнес-логика | `shop/services.py` | `calculate_order()` считает сумму, скидку и итог; `is_discount_applicable()` проверяет условие скидки; `create_purchase()` атомарно сохраняет заказ с позициями |
| Формы | `shop/form.py` | `PurchaseForm` (ModelForm): имя и адрес плюс динамические поля количества для каждого товара каталога, проверка «выбран хотя бы один товар» |
| **Controller** (view) | `shop/views.py` | `index` (каталог), `PurchaseCreate` (FormView): только связывает форму, сервис и шаблон |
| **View** (template) | `shop/templates/shop/*.html` | каталог, форма заказа, страница с итогом заказа |
| Маршруты | `shop/urls.py` | `/`, `/order/` (заказ из нескольких товаров), `/buy/<id>/` (тот же заказ с предвыбранным товаром) |

Расчёт скидки вынесен из контроллера и модели в отдельный модуль сервисов. Поэтому его можно
тестировать без HTTP-запросов, а контроллер остаётся «тонким».

### Изменения в БД

- миграция `0002_purchase_items_and_discount`: у `Purchase` убрано поле `product`, добавлены `subtotal`,
  `discount`, `total`; создана модель `PurchaseItem`;
- фикстура `products.yaml` заполнена товарами магазина одежды (футболка, джинсы, куртка, свитер,
  кроссовки, шапка);
- модели зарегистрированы в админке (заказ показывается вместе с позициями).

## Запуск

Нужен PostgreSQL с базой `django_db`. Например, в Docker:

```powershell
docker run -d --name ptlab2-postgres -e POSTGRES_PASSWORD=ps_password -e POSTGRES_DB=django_db -p 5432:5432 postgres:16-alpine
```

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

$env:DATABASE_PASSWORD = "ps_password"
python manage.py migrate
python manage.py loaddata products.yaml
python manage.py test shop/tests/
python manage.py runserver        # http://localhost:8000
```

Параметры подключения задаются переменными окружения `DATABASE_NAME`, `DATABASE_USER`,
`DATABASE_PASSWORD`, `DATABASE_HOST`, `DATABASE_PORT` (по умолчанию `django_db`, `postgres`, пустой
пароль, `localhost`, `5432`).

## Используемые технологии

- **Python 3.12**, **Django 5.2**: MVC (MTV) веб-фреймворк, ORM, миграции, формы, class-based views;
- **PostgreSQL 16** (в Docker), драйвер `psycopg2-binary`;


| Модуль | Что проверяется |
|---|---|
| `test_models.py` | типы и значения полей `Product`, `Purchase`; значения по умолчанию; связь заказа с позициями и стоимость позиции |
| `test_services.py` | нет скидки для одного вида товара; скидка 10% для разных товаров; нулевое количество не учитывается; сохранение заказа; отказ на пустой заказ |
| `test_views.py` | доступность каталога, страницы заказа и `/buy/<id>/`; оформление заказа со скидкой через POST |

## Выводы

1. Разобрано разделение ответственности в MVC на примере Django: модели описывают данные и связи,
   шаблоны отвечают только за отображение, а view (контроллер) обрабатывает запрос и выбирает ответ.
2. Чтобы контроллер не разрастался, бизнес-логика (расчёт скидки) вынесена в модуль сервисов, а работа
   с пользовательским вводом и его проверка вынесены в форму (`form.py`). Каждый слой можно проверить
   отдельно модульными тестами.
3. Переход от «одна покупка = один товар» к заказу с позициями потребовал изменить схему БД.
   Механизм миграций Django позволил сделать это декларативно, а сохранение цены в позиции заказа
   защищает историю покупок от последующих изменений цен.
4. Доработка выполнена в отдельной ветке и влита в основную только после прохождения всех тестов,
   поэтому основная ветка всё время оставалась рабочей.
